# 小红书自动选题 / 出图 / 半自动发布流水线

## Summary

在 TLDRChinese 现有的每日新闻流水线后面接一段：每天自动从当天新闻里选出 3 条最有传播潜力的，每条**独立**生成一篇小红书笔记（配图 + 标题 + 正文 + 标签），跑完输出一个 HTML 审核页；人挑其中 1 篇，由 ego-browser 执行发布。

---

## Problem Frame

TLDRChinese 已经有三条分发渠道在跑：网站、邮件 newsletter、微信公众号（Make.com 编排）。小红书是唯一没打通的，而它是这四条里唯一有自然流量分发的平台——前三条都依赖用户主动找过来。

没打通的原因不是不想做，是单篇成本太高。手动做一篇小红书科技笔记要走：翻当天新闻挑选题 → 判断哪条中文读者会有反应 → 排版出图 → 写符合小红书语感的标题和正文。一篇 20-30 分钟，一周就是两三个小时，坚持不下来。

但这条链里大部分工作量其实已经有资产托底：新闻已经翻译好躺在 MongoDB 里，`api/services/image_extractor.py` 已经在做原文配图提取，DeepSeek 的 key 和调用封装都在。真正缺的只有三样——选题判断、出图、以及一个能让人在一分钟内决定"发不发"的审核入口。

---

## Key Decisions

**一条新闻一篇笔记，一天出 3 篇候选，人工挑 1 篇发。** 不做"今日科技 3 条"这种合集型日报。单话题笔记的标题和正文能完全围绕一个点写，钩子更锐，在小红书上单话题也比合集型更容易起量。更重要的是，这个形态把最终选题权留给人：自动打分只需要做到"选出 3 个不差的"，不需要做到"选出 1 个最好的"，容错空间大得多。

**图片走 HTML 模板截图，不用 AI 生图。** 中文文字在图像生成模型里会糊、会写错字、会出现不存在的字形，不能拿来做承载正文的卡片。HTML 模板 + headless Chrome 截图既保证文字锐利，也保证跨天风格统一——统一的视觉是账号识别度的一部分。AI 生图最多用在装饰性背景上，不用在这一版。

**配图优先复用原新闻的图。** 项目里已有配图提取能力，原文配图（产品截图、发布会照片、图表）比纯排版卡片更有信息量也更抓眼。提取失败时降级到纯排版模板，不阻塞出稿。

**半自动发布，不做全自动。** 全自动每天只省 2 分钟，换来的是账号被限流的风险、一个登录态过期就静默失败的环节，以及内容发错事后才知道。人工确认这一步保留，它同时也是内容质量的最后一道闸。

**云端选题，本地出图和发布。** 选题打分是纯 API 调用，挂在现有 Vercel cron 之后最省事。出图和发布必须落在本地 Mac——ego-browser 要真实浏览器和用户登录态，没法搬到 serverless。

**HTML 审核页是唯一的交互界面。** 不做通知加文件夹那套。跑完输出一个页面，3 篇候选的成图和文案摆在一屏，打开就能挑。

**引流只放简介和评论区置顶，正文不硬导。** 小红书会限流带明显导流意图的笔记。正文按"自己讲完整"的标准写，引流靠账号简介和长期心智，慢但不打架。

---

## Actors

- A1. 每日生成流程 — 自动跑，负责选题打分、出图、写文案、产出审核页
- A2. 运营者（你） — 打开审核页，挑一篇，触发发布
- A3. ego-browser — 执行发布动作，登录态失效时把控制权交还 A2

---

## Requirements

**选题**

- R1. 每天从当天 TLDRChinese 新闻中选出 3 条候选，每条独立成篇。
- R2. 打分维度显式定义且可调，至少覆盖：中文读者对该主体的认知度、是否有冲突或反差、是否有数字冲击力、与普通人生活的相关度。
- R3. 已经出过稿的新闻不重复进入候选。

**出图**

- R4. 每篇笔记产出 3-4 张图，尺寸 1080×1440（3:4）。
- R5. 首图是钩子封面，承载标题的核心冲突点，不是新闻标题的直译。
- R6. 优先复用原新闻配图；提取失败时降级到纯排版模板，不中断出稿。
- R7. 图中所有文字由 HTML 渲染，不经过图像生成模型。

**文案**

- R8. 标题 ≤20 字符（保守控制在 18 以内）。
- R9. 正文 ≤1000 字符（保守控制在 950 以内）。
- R10. 正文自身信息完整，读者不点进原文也能获得完整判断。
- R11. 每篇配 3-6 个标签。

**审核与发布**

- R12. 流水线每次跑完产出一个 HTML 审核页，3 篇候选一屏可比。
- R13. 审核页直接展示成图（不是描述、不是文件路径），文案可一键复制。
- R14. 选定后由 ego-browser 完成上传图片、填标题正文标签、发布。
- R15. 登录态失效时交还浏览器控制权并明确提示扫码，不静默失败也不自动重试。

---

## Key Flows

- F1. 每日生成
  - **Trigger:** 当天新闻已入库后触发（现有 21:00 UTC cron 之后）。
  - **Actors:** A1
  - **Steps:** 拉取当天新闻 → 逐条打分 → 取 top 3 → 每条提取配图 → 渲染 3-4 张卡片截图 → 生成标题/正文/标签 → 字数自检 → 产出 HTML 审核页。
  - **Outcome:** 本地存在一份当日审核页和 3 套成图。
  - **Covered by:** R1, R2, R3, R4, R5, R6, R7, R8, R9, R10, R11, R12, R13

- F2. 审核与发布
  - **Trigger:** A2 打开当日审核页。
  - **Actors:** A2, A3
  - **Steps:** 浏览 3 篇候选 → 指定发哪一篇（必要时先改文案）→ A3 打开创作平台上传发布 → 回报结果。
  - **Outcome:** 一篇笔记发布成功，或明确报错。
  - **Covered by:** R12, R13, R14

- F3. 登录态失效
  - **Trigger:** A3 执行发布时发现未登录。
  - **Actors:** A3, A2
  - **Steps:** A3 停止操作 → 交还控制权并提示扫码 → A2 扫码后确认继续 → A3 接管并续跑发布。
  - **Outcome:** 发布完成，或 A2 选择放弃且状态明确。
  - **Covered by:** R15

## Acceptance Examples

- AE1. **Covers R3.** 某条新闻昨天已被选为候选并出过图，今天新闻列表里仍然存在同一条 → 今天的 3 条候选中不出现它。
- AE2. **Covers R6.** 某条新闻的原文页无法提取到可用配图 → 该篇仍然产出 3-4 张纯排版卡片，审核页正常展示，不因缺图跳过这条。
- AE3. **Covers R8, R9.** 生成的标题为 23 字符 → 在产出审核页之前自动重写至 ≤20，不把超限内容送到审核页。
- AE4. **Covers R15.** 发布时 cookie 已过期 → 流程停在扫码提示上，不重试、不换账号、不把失败当成功回报。
- AE5. **Covers R1.** 当天新闻总数少于 3 条可用条目 → 产出实际数量的候选并在审核页说明，不用低质条目凑满 3 篇。

---

## Success Criteria

- 从打开审核页到决定发哪篇，用时在 1 分钟以内。
- 3 篇候选里至少有 1 篇是运营者愿意发的——低于这个比例说明打分维度没调对，选题环节的价值不成立。
- 端到端跑一次不需要人改代码或改 prompt。
- 单篇从生成到发布出去的人工时间，从现在的 20-30 分钟压到 3 分钟以内。

---

## Scope Boundaries

**MVP 只做**

一套图片模板、每天 3 条候选、HTML 审核页、由人在会话里指定发哪篇。跑通端到端优先于任何优化。

**Deferred for later**

- 未选中的另外 2 篇候选的复用和排期（MVP 里就是丢弃）。
- 审核页内嵌发布按钮（MVP 里由人在会话中口头指定）。
- 多套模板 / 按新闻类型切换版式。
- 发布数据回流——用实际点赞收藏反过来校准打分维度。
- 视频、图文以外的形态。

**Outside this product's identity**

- 全自动发布。它省的时间不值一个天天可能挂的环节，也拿掉了内容质量的最后一道闸。
- `write-xiaohongshu` skill 那套"先研究同类爆款再动笔"的流程。它整条依赖小红书 MCP，当前环境没有装，不作为本次的前提。
- 账号定位、头像、简介的重做。

---

## Dependencies / Assumptions

- 当天新闻在选题环节触发前已经完成翻译并入库。选题不负责抓取和翻译。
- 出图和发布依赖本地 Mac 处于唤醒状态且 ego-browser 可用。Mac 关机的那天没有产出，且不做云端兜底——因为流程本来就需要人在场。
- 小红书登录 cookie 会周期性失效，需要人工扫码续期。频率未知，按每几周一次假设。
- **未验证：** 小红书对 ego-browser 这类浏览器自动化发布的检测强度。1k 粉的老账号被限流的代价由运营者自行承担；如果观察到异常，回退到完全手动发布。
- **未验证：** 现有 Vercel Python 环境是否方便挂载额外的打分任务，还是选题也一并放本地更简单。
